## 2. Phase-1 차단 요소 (Blockers)

### 🔴 B1. 이미지 필드 추가

#### 배경
현재 통합 스키마에 이미지 관련 필드가 없으나, **카드 미리보기와 상세페이지 갤러리 모두 이미지가 필수**임.

#### 협의 결정 사항

| 필드명 | 타입 | 설명 | 비고 |
|---|---|---|---|
| `thumbnail_url` | varchar(500) | 카드용 썸네일 URL | 목록 화면용 |
| `image_urls` | jsonb (string[]) | 상세페이지 갤러리용 URL 배열 | 0~N개 |
| `image_count` | int | 보유 이미지 개수 | 캐싱/UI 최적화용 |

#### 공공 API별 매핑 가이드

| 공공 API | 이미지 필드 (확인 필요) | 매핑 방식 |
|---|---|---|
| GoCamping (한국관광공사) | `firstImageUrl`, `firstImageUrl2`, `imageList` | thumbnail_url ← firstImageUrl, image_urls ← imageList 파싱 |
| 산림청 휴양림 | TBD | 협의 필요 |
| 국립공원공단 | TBD | 협의 필요 |

#### 결정 필요 질문
- Q. 위 필드 정의 그대로 채택할 것인가?
- Q. 공공 API별 이미지 필드의 정확한 명세 확인 (백엔드 조사 필요)
- Q. 썸네일 사이즈 가공 정책 (원본 그대로 vs 리사이징)

### 🔴 B2. 이미지 호스팅 정책

#### 배경
공공 API의 이미지 URL을 그대로 참조할지, 자체 스토리지로 다운로드할지 결정 필요.

#### 옵션 비교

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. Pass-through (원본 URL 그대로)** | 빠른 구현, 저장 공간 불필요 | 원본 서버 다운/URL 변경 시 깨짐, CDN 최적화 불가, 외부 트래픽 의존 |
| **B. 자체 스토리지(S3/R2) 다운로드** | 안정성, WebP/리사이징 최적화, 워터마크 가능 | 스토리지 비용, ETL 복잡도 증가 |

#### 권장
- **Phase-1: A (Pass-through)** — 빠른 출시 우선
- **Phase-2 이후: B로 전환** — 안정성/성능 확보 후 차별화

#### 결정 필요 질문
- Q. Phase-1 권장안(Pass-through)에 동의하는가?
- Q. Phase-2 전환 시 마이그레이션 전략은?

### 🔴 B3. 이미지 부재 시 처리 정책

#### 배경
공공 API 데이터의 상당수가 이미지를 갖고 있지 않음. 검색 결과/큐레이션에서 어떻게 처리할지 결정 필요.

#### 옵션
- **A. 검색 결과에서 제외** (이미지 있는 장소만 노출)
- **B. 노출하되 플레이스홀더 처리** (BI 일러스트 등)

#### 권장
- **B (노출 + 플레이스홀더)** — 데이터 양 확보 우선, 사용자가 모든 정보를 볼 수 있어야 함

#### 결정 필요 질문
- Q. 권장안(B)에 동의하는가?
- Q. 플레이스홀더 이미지 호스팅 위치 (디자인 에셋으로 프론트 번들 vs CDN)
- Q. 추후 사용자/관리자가 이미지를 업로드할 수 있는 기능 계획이 있는가?

- Q. 카테고리는 features의 특수 타입인가, 별도 상위 분류인가? (정규화 모델 결정)

### 🔴 B5. features / amenities 마스터 데이터 처리

#### 배경
필터 모달의 "특징(features)"과 "부대시설(amenities)" 옵션 목록을 어떻게 관리하고 프론트로 전달할지 결정 필요.

#### 옵션 비교

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. 프론트 하드코딩 (정적 enum)** | 구현 단순, 타입 안정성, 초기 로딩 빠름 | 옵션 변경 시 프론트 배포 필요, 백엔드와 불일치 가능 |
| **B. 백엔드 마스터 API (동적)** | 프론트 배포 불필요, 데이터 일관성, 다국어 처리 용이 | API 호출 추가, 마스터 관리 인프라 필요 |
| **C. 하이브리드 (백엔드 우선 + fallback)** | 안정성 | 구현 복잡도 높음, 동기화 부담 |

#### 권장
- **Phase-1 권장: B (백엔드 마스터 API)**
- ETL 정규화는 어차피 필요한 작업이므로 그 결과물을 마스터 API로 노출
- 어드민 페이지 없이 DB seed/마이그레이션으로 관리 가능
- 캐싱으로 성능 영향 최소화

#### API 설계 제안 (옵션 B 기준)
```
GET /api/v1/meta/features
응답: [
  {
    code: "walk_in",
    label: "도보 진입",
    icon: "walk",
    sort_order: 1,
    group: "access"
  },
  ...
]

GET /api/v1/meta/amenities
응답: [...]
```

#### 결정 필요 질문 (협의 시 던질 질문)

##### Q1. 현재 ETL 설계에서 features/amenities 정규화 계획이 있는가?
- 있다면: 정규화 결과물이 마스터 테이블 형태인가?
- 없다면: 정규화 작업의 우선순위와 범위는?

##### Q2. 마스터 데이터 관리 인프라가 있는가?
- 어드민 페이지: 있는가? Phase-1에 만들 계획인가?
- DB seed: 코드로 관리 vs DB 마이그레이션 vs 어드민 입력
- 변경 빈도: 한번 정의 후 거의 변경 없음 vs 자주 추가/수정

##### Q3. 다국어 지원 계획이 있는가?
- Phase-1: 한국어만
- Phase-2+: 영어 등 추가 가능성?
- 다국어 시 라벨 관리 위치

##### Q4. 마스터 데이터의 메타 속성은 무엇이 필요한가?
- code (필수)
- label (필수)
- icon (디자인 시스템 아이콘 키)
- description (툴팁용)
- sort_order (필터 모달 노출 순서)
- group (예: features 안에서 "접근성" / "환경" / "활동" 등 그룹핑)
- is_active (비활성화 가능 여부)

##### Q5. API 캐싱 전략은?
- 옵션 B 채택 시 마스터 데이터 변경 빈도 낮음 → 장기 캐싱 적합
- HTTP Cache-Control max-age (1시간 ~ 1일)
- ETag 기반 검증
- 클라이언트 TanStack Query staleTime 설정

##### Q6. 카테고리(Category)와 features의 관계
- 카테고리(산·숲, 바다 등 6개)도 마스터 데이터의 일종
- features와 어떻게 구분할 것인가?
- 추정: 카테고리는 상위 분류, features는 세부 특징
- 데이터 모델에서 별도 필드 vs features의 특수 타입

##### Q7. ETL 단계의 정규화 매핑 정책
- 공공 API 3종(GoCamping, 산림청, 국립공원)에서 features/amenities 표현 방식이 다름
- GoCamping: `sbrsCl` 콤마 구분 문자열 추정
- 산림청: 별도 필드 분리 또는 boolean 플래그 추정
- 국립공원: 자유 텍스트 또는 코드 추정
- 어떻게 정규화 매핑 테이블을 관리할 것인가?

#### 임시 처리 방침 (협의 전까지)
- 화면 정의서: 필터 모달의 "특징"/"부대시설" 섹션을 "마스터 데이터 의존"으로 명시
- API 명세: 데이터 출처 "백엔드 협의 후 확정" 표기
- 데이터 키 형태(`features[]`, `amenities[]`)는 변경 없음

### 🔴 B6. 운영 상태 데이터 정제 정책

#### 배경
화면 정의 결정으로 검색 결과에는 **운영중 장소만 노출**하기로 함. 백엔드 ETL/API에서 어떻게 처리할지 정의 필요.

- Q. 어떤 상태값을 "노출 제외" 대상으로 분류할 것인가?

## 3. Phase-1 진행 중 협의 사항

### 🟡 P1. 수동 큐레이션 인프라

#### 배경
홈 화면의 "백패킹 성지", "한번쯤 가볼만한 야영지" 두 큐레이션 섹션은 **수동 큐레이션** 방식. 운영 인프라 결정 필요.

#### 옵션
- **A. 어드민 페이지** — UI로 ID 추가/삭제/순서 변경
- **B. 환경변수** — 코드 배포로 관리
- **C. DB 테이블 + 코드 배포** — 마이그레이션으로 추가/삭제

#### 권장
- **C (DB 테이블) + Phase-2에 어드민 페이지 추가** — 기능 확장성과 초기 단순성의 균형

#### 결정 필요 질문
- Q. 권장안에 동의하는가?
- Q. 어드민 페이지 구축 우선순위는?
- Q. 큐레이션 변경 빈도 예상치는?

#### API 설계 제안
```
GET /api/v1/curations/legendary    → 백패킹 성지 ID 목록
GET /api/v1/curations/recommended  → 한번쯤 가볼만한 야영지 ID 목록
```

응답에는 카드 노출에 필요한 최소 필드만 포함 (이미지, 지역, 타이틀).

  - 옵션 2: 별도 "데이터 출처" 페이지 운영
- Q. 자체 사용자 업로드 이미지가 추가될 경우 권리 처리는?

### 🟡 P3. 사용자 인증 & 세션 관리

#### 배경
구글 OAuth + 사용자 상태 관리 필요. 프론트엔드와의 인터페이스 정의 필요.

  tier: "free" | "member"

```

##### Q4. OAuth 콜백 URL
- `/auth/callback` 또는 별도 정의?

##### Q5. 로그아웃 API
- `POST /api/v1/auth/logout` 정의 필요
- 서버 세션 무효화 방식

##### Q6. 신규 사용자 가입 처리
- OAuth 첫 로그인 시 자동 회원 생성 vs 별도 가입 API
- 닉네임 자동 생성 정책 (구글 프로필명 vs 자동 생성)

### 🟡 P4. 온보딩 응답 저장 API

#### 배경
온보딩 5단계 응답을 단계별로 저장. 부분 저장 정책과 API 설계 필요.

#### 핵심 요구사항
- 각 단계 응답을 즉시 저장 (전체 완료까지 대기 X)
- 사용자 이탈 후 재진입 시 이전 응답 복원
- 이전 단계로 이동해 응답 수정 가능 (Phase-1)
- 5단계 모두 완료 시 `onboarding_completed_at` 기록

#### API 설계 제안

```
POST /api/v1/onboarding/responses
Body: {
  step: 1,
  data: { experience_level: "intermediate" }
}
응답: {
  completed_steps: 1,
  onboarding_completed_at: null
}

GET /api/v1/onboarding/responses
응답: {
  responses: {
    1: { experience_level: "intermediate" },
    2: { preferred_styles: ["ultralight"] },

## 4. 기술부채 (Phase-2 이후)

### 🟢 D1. 평점/리뷰 시스템

#### 배경
사용자 의사결정 핵심 정보. Phase-1엔 평점 데이터가 없어 카드/상세페이지에서 제외했지만, **반드시 추가되어야 할 기능**.

#### 협의 필요 항목 (Phase-2 시점)
- 데이터 모델: 평점/리뷰/사진리뷰 분리 vs 통합
- 평점 집계 방식 (단순 평균 vs 가중 평균)
- 어뷰징 방지 (1인 1리뷰, IP/디바이스 제한, 신고 시스템)
- 작성 권한 (방문 인증 필요 여부)
- 리뷰 노출 정렬 정책
- 외부 평점 데이터 연동 가능성 (구글 플레이스, 네이버 등)

---

### 🟢 D2. 가격 데이터 수집 전략

#### 배경
공공 API에는 가격 정보 미제공. 사용자가 매우 궁금해하는 정보임.

#### 옵션 (Phase-2 검토)
- 사용자 제보 (UGC)
- 크롤링 (법적/윤리적 검토 필요)
- 제휴 (예약 사이트, 캠핑장 직접 제휴)
- 수동 입력 (운영진 또는 어드민)

#### 비즈니스 모델 연계
- C2C 중고장터, 제휴 수수료 모델과 자연스럽게 연결
- 무료/유료 구분만으로도 큰 가치

---

### 🟢 D3. 지도 기반 탐색

#### 배경
Phase-1엔 텍스트 검색만. 위치/지도 기반 탐색은 Phase-2+.

#### 선결 조건
- 좌표 데이터 정제 (현재 스키마에 lat/lng 필드 확인 필요)
- 좌표 정확도 검증
- 지도 API 선정 (네이버/카카오/구글)
- 비용 정책 (지도 API 호출 비용)

#### 결정 필요 질문 (Phase-2 시점)
- Q. 현재 스키마에 좌표 필드가 있는가? 데이터 채워져 있는가?
- Q. 어떤 지도 API를 사용할 것인가?
- Q. 클러스터링 정책

---

### 🟢 D4. 위치 기반 탐색

#### 배경
"내 주변 캠핑장" 등 사용자 현재 위치 기반 검색.

#### 선결 조건
- D3(지도 기반)와 동일한 좌표 데이터
- 사용자 위치 권한 처리 (PWA 환경)
- 거리 기반 정렬 인덱싱 (PostgreSQL PostGIS 등)

### 🟢 D5. 데이터 품질 관리 (F4)

#### 협의 필요 항목 (Phase-2 시점)
- ETL 파이프라인 모니터링
- 중복 데이터 감지/병합
- 누락 필드 보정 (사용자 제보 + 자동 보강)

- 데이터 품질 지표 정의 (완전성, 정확성, 일관성)

## 6. 협의 진행 가이드

### 6.1 협의 우선순위

| 순서 | 항목 | 사유 |
|---|---|---|
| 1 | B1 (이미지 필드) + B2 (호스팅 정책) + B3 (부재 처리) | 모든 화면의 핵심 요소, 함께 결정 필요 |
| 2 | B4 (카테고리 매핑) | 홈/검색 화면 차단 |
| 3 | B5 (마스터 데이터) | 필터 기능 차단, ETL 정규화와 직결 |
| 4 | B6 (운영 상태 정제) | 검색 API 동작 정의 |
| 5 | P3 (인증/세션) + P4 (온보딩 API) | 인증 플로우 구현 시작 시점에 필요 |
| 6 | P1 (큐레이션) + P2 (저작권) | 기능 구현 마지막 단계에 필요 |

### 6.2 협의 형식 제안
- **1차 미팅 (60분)**: B1~B6 (Blockers) 일괄 협의
- **2차 미팅 (45분)**: P1~P4 협의 + 1차 미해결 사항 정리
- **이후**: 각 항목 결정 후 본 문서 업데이트, 결정 사항을 별도 결정 로그(Decision Log)로 관리

### 6.3 결정 후 후속 작업
- 본 문서를 **결정 결과**로 업데이트 (`status: 협의 필요` → `status: 확정`)
- API 명세서에 반영
- 화면 정의서에 영향이 있는 결정은 화면 정의서 업데이트
- ETL/DB 마이그레이션 작업 티켓 생성
